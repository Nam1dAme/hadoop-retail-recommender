# GPU 优化实验方案

日期：2026-10-22；状态：**方案，尚未执行优化实验**。本方案在 W11 本机验证和报告归档后整理；原项目完整结项仍待独立物理盘备份，见 [W11 记录](execution/2026-10-22-w11.md)。

目标：在当前 Ryzen9 7940HX / RTX4060 Laptop 8GiB / WSL 约7.4GiB 环境上，展示瓶颈定位、逐步优化及 GPU 适用规模。以同模型、同 batch、同 FP32 的 GPU 至少 **2×** 提速作为实验目标，实际是否达到以重复测量为准。

## 1. 保留原基准，建立独立实验

原 W07 CPU/CUDA 五轮训练中位数 13.345/25.251 秒，CPU÷GPU=0.5285×。模型为 GMF16 + MLP32→64→32→16，batch1024，FP32，固定样本与种子。该结果继续作为原项目验收证据。

优化实验建议新增独立 runner 和 `var/benchmarks/gpu-opt/<trial-id>/` 归档，读取已校验的 EVAL TRAIN 样本，使用独立模型/优化器副本。原 `benchmark` 的固定1024批量、模型结构、FP32及六条数据库记录保持原定义；新试验的数据结构、计时口径及变化项单独记录。

当前五轮共 4,060,650 条样本。两个 int64 ID 加一个 FP32 标签，张量本体约 77.5MiB，适合优先试验整组样本驻留显存；这不包含模型、梯度、优化器、工作区和 PyTorch 缓存，实际峰值仍需测量。

## 2. 分阶段路线

| 阶段 | 改动 | CPU/GPU 如何比较 | 用途 |
|---|---|---|---|
| G0 当前环境基线 | 用独立副本复测原设置，固定样本和顺序 | 同结构、batch1024、FP32，各3次 | 确认当前设备状态；原 W07 结果另行保留 |
| G1 数据常驻显存 | 样本预先转为张量，一次传入 GPU，按切片训练 | CPU样本驻内存，GPU样本驻显存；同模型/batch/FP32；另列首次搬运和端到端耗时 | 测量逐批传输带来的实际影响 |
| G2 减少调度开销 | 分别试 `torch.compile(mode="reduce-overhead")` 和 `Adam(fused=True)`，再试组合 | 保持样本、结构、batch、FP32；CPU保留对应最佳适用实现；单列编译成本 | 逐项解释小算子、Python调度和优化器开销 |
| G3 批量扫描 | 测1024、4096、8192，显存允许时再试16384 | 每个batch都运行CPU和GPU；CPU额外测1/4/8线程，记录最快合理线程配置及原4线程结果 | 查找当前模型的吞吐量拐点 |
| G4 模型规模扫描 | 仅当前小模型优势仍不足时，运行下表的中/大模型 | 同一规模内双方使用相同结构、batch、样本、精度、训练轮数 | 展示计算密集程度变化后的设备差异 |
| G5 混合精度附加实验 | 对已选GPU配置测试AMP FP16；设备支持时再测BF16 | GPU FP32与GPU AMP分组；与CPU FP32的配置级比较另行标注精度差异 | 展示混合精度的额外收益 |

编译可减少 Python 调度及部分内存读写开销，收益依赖模型和 batch；首次编译可能使短任务总耗时更长。官方说明见 [编译端到端教程](https://docs.pytorch.org/tutorials/intermediate/torch_compile_full_example.html)。本机已核对 PyTorch2.6.0+cu124 的 `torch.compile` 含 `mode` 参数、Adam 含 `fused` 参数；接口存在不等于已证明该组合在当前模型上可用或更快，编译失败/回退要进入结果记录。

显存无法容纳全部输入时，再测试 pinned memory、`non_blocking` 与预取的组合。应设计可重叠的数据通路，避免每个 batch 临时 pin 一次；实际收益需要测量。[官方传输教程](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)

AMP 的收益更依赖充足计算量，小模型未充分占用 GPU 时改善可能有限。它会改变部分运算精度，应检查损失、梯度及验证指标。[官方 AMP 教程](https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html)

建议按阶段逐项测量，不一次组合所有开关。每配置先试跑一次筛选，保留全部试跑结果；最终候选重新使用独立进程各运行三次。达到目标后即可停止扩大规模。

## 3. 推荐的规模对照

| 规模 | GMF用户/商品向量 | MLP用户/商品向量 | MLP层宽 | 融合输出 |
|---|---:|---:|---|---|
| 原模型 | 各16维 | 各16维 | 32→64→32→16 | 32→1 |
| 中模型 | 各64维 | 各64维 | 128→256→128→64 | 128→1 |
| 大模型 | 各128维 | 各128维 | 256→1024→512→128 | 256→1 |

中/大模型先试4096和8192批量。它们用于检验同一推荐任务在更高计算量下的硬件特性，各自训练独立参数；它们的速度与效果都不能替代原模型结果。仅增加重复样本量未必改变小模型每批的计算瓶颈，因此优先比较数据通路、批量和模型规模。

同一规模的 CPU/GPU 使用相同样本、标签、初始化种子、Adam超参数和轮数。不同 batch 会改变参数更新次数，因此跨 batch 的结论同时报告验证质量，不能只比较时间。

## 4. 计时与正确性

**同时给出三种时间：**

1. 首次运行总耗时：输入读取、张量准备、设备传输、编译/预热、训练、验证和保存；另列各阶段。
2. 可重复的训练流程耗时：扣除一次性编译后，包含该配置所需数据传输及训练，说明输入驻留方式。
3. 驻留数据的稳态训练耗时：GPU边界同步，预热后重置模型/优化器/随机状态；各配置处理同样完整样本和五轮，记录 samples/s。

三种口径各自计算加速比，不用 GPU 稳态时间除以 CPU 端到端时间。编译开销单独展示，即使稳态更快，也保留首次运行更慢的事实。Profiler 采样与正式计时分开，先定位 H2D copy、CPU等待、算子调用、矩阵计算、embedding和Adam各部分，再测最终性能。

每次记录 loss曲线、样本数/哈希、设备位置、有限梯度、权重是否更新、checkpoint重载结果，以及CPU线程、精度、TF32、确定性、库版本、驱动、电源模式、显存峰值与WSL内存口径。重任务持有项目共用锁，串行运行；使用已有依赖锁，保持当前驱动和全局环境。

FP32实现优化先比较相同初始状态和固定小批次的logit/loss，报告最大绝对及相对差异；训练后比较相同VALIDATION/WARM候选上的NDCG、Recall和覆盖。预先固定可接受误差和质量变化范围，不能看结果后放宽。AMP单独设定并报告数值与质量容差。

原 TEST 已封存，优化配置与模型规模的选择使用 TRAIN/VALIDATION。正式 FULLFIT推荐、ALS默认算法、当前release和原CPU/GPU表继续使用原产物。需要将优化模型正式发布时，另行定义协议版本、独立实验及相应验收，避免将这份性能方案隐式变成新正式模型。

资源预检设置：整组输入连同模型/优化器的预计峰值应留足显存余量；建议以实际峰值低于约6GiB、WSL至少保留约1.5GiB可用内存作为本机试跑预算。若超过预算，减少batch或评分块，保留失败记录，不能用OOM后剩余样本计算吞吐量。

## 5. 演示交付

最小交付建议为独立 CLI runner、可追溯JSON/CSV、Profiler结果和离线HTML报告，使用当前Plotly即可制作图表。网页模型实验区的进一步接入属于后续接口/UI扩展，本方案阶段先交付独立可打开的报告。

报告包含三组图：原项目 CPU/GPU结果；相同模型逐项优化前后的耗时/吞吐量；模型规模×batch的加速比。首次编译时间与稳态时间并列，AMP有独立精度标记。所有候选和失败试跑可查，选定配置由三次重复结果支持。

现场可用约一分钟展示已预热的CPU与GPU训练进度，同时观察 `nvidia-smi`，随后打开对应trial报告核对样本、loss和时间。若展示预热后的速度，应在界面明确说明；准备好的历史结果与现场运行各自标明时间。

**建议优先实施 G0—G3。** 若原模型仍未达到2×目标，使用G4展示计算规模与GPU优势的关系，再用G5单独展示精度优化。预期交付是可复核的性能变化及适用条件，最终速度、质量和最佳配置均等待实测。
